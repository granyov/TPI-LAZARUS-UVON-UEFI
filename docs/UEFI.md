# Как плата работает как машина с UEFI

Отдельной UEFI-прошивки в цепочке нет. Её роль играет U-Boot 2024.04,
собранный с `EFI_LOADER`: он поднимает UEFI-сервисы, находит загрузчик
операционной системы и передаёт ему управление по обычным правилам UEFI.
Для ОС плата при этом неотличима от любой другой машины с UEFI.

## Что включено

| Опция | Что даёт |
|---|---|
| `CONFIG_EFI_LOADER` | сами UEFI-сервисы: протоколы, память, устройства |
| `CONFIG_EFI_BOOTMGR` | загрузочный менеджер и переменные `Boot####`, `BootOrder` |
| `CONFIG_EFI_VARIABLE_FILE_STORE` | EFI-переменные хранятся файлом `ubootefi.var` на ESP |
| `CONFIG_CMD_BOOTEFI` | ручной запуск `.efi`-образа из консоли |
| `CONFIG_CMD_EFIDEBUG` | просмотр и правка загрузочных записей |

## Что нужно на носителе

Ровно то же, что любой машине с UEFI:

1. Таблица разделов **GPT**.
2. Раздел **ESP** с типом `C12A7328-F81F-11D2-BA4B-00A0C93EC93B` (код `EF00`),
   файловая система FAT32.
3. Внутри него `\EFI\BOOT\BOOTAA64.EFI` — загрузчик ОС.

Ядро и всё остальное лежат где угодно, откуда их прочитает этот загрузчик:
U-Boot умеет FAT и ext4, GRUB — тем более.

## Как выбирается, с чего грузиться

Команда по умолчанию — `scsi scan; bootflow scan -lb`. Сперва инициализируется
SATA, затем перебираются носители. Устроено это двумя разными механизмами, и
разница между ними неочевидна.

**Метод `efi`** перебирает разделы каждого устройства и ищет на них
`\EFI\BOOT\BOOTAA64.EFI`. Он **проверяет тип раздела** и берёт только те, у
которых стоит тип ESP. Раздел с посторонним типом в списке `bootflow scan -l`
не появится вовсе.

**Менеджер `efi_mgr`** идёт первым (`Order 0`) и работает иначе: он опирается на
сохранённые EFI-переменные `Boot####` и `BootOrder`, а при их отсутствии
перебирает носители сам. Тип раздела он при этом **не проверяет** — найдёт ESP
и с посторонним типом.

Отсюда практический вывод: **порядок загрузки при нескольких носителях с ESP
не гарантирован**. `efi_mgr` может выбрать не то устройство, которое вы
ожидаете, потому что его выбор зависит от переменных, оставшихся с прошлых
загрузок. Если на плате есть несколько загрузочных носителей, надёжнее оставить
ровно один, а остальные обезоружить — например, переименовав на них
`BOOTAA64.EFI`.

Посмотреть, что видит загрузчик:

```text
=> bootflow scan -l          # перебрать заново и показать найденное
=> bootflow list             # показать найденное ранее
=> bootflow select 1         # выбрать конкретный
=> bootflow boot             # загрузиться с выбранного
```

Загрузочные записи UEFI:

```text
=> efidebug boot dump
```

## Запуск вручную

Если автоматический выбор не устраивает, загрузчик ОС запускается напрямую:

```text
=> fatload mmc 2:1 0x10000000 EFI/BOOT/BOOTAA64.EFI
=> bootefi 0x10000000
```

Так, например, запускается носитель, которого нет в списке `bootflow`: карта
microSD сидит на SDMMC2, а этот контроллер в перечень загрузочных устройств
U-Boot не входит.

## Device tree для операционной системы

U-Boot кладёт свой control DTB в EFI configuration table, и загрузчик ОС может
им воспользоваться. Но обычно ОС подсовывает собственный: GRUB делает это
командой `devicetree`, после чего в журнале ядра видно

```text
EFI stub: Using DTB from configuration table
```

Так устроено потому, что device tree, нужный ядру, богаче того, что достаточно
самому загрузчику.

## Чего здесь нет

- **Secure Boot** не включён: подписи образов не проверяются. Целостность на
  уровне прошивки обеспечивает другое — заводской MiniLoader сверяет SHA-256
  каждого компонента FIT до передачи управления и не запустит повреждённый.
- **Графической оболочки настроек** нет. Всё управление — из консоли U-Boot
  командами `bootflow` и `efidebug`.
- **ACPI** не используется: описание оборудования передаётся через device tree.
