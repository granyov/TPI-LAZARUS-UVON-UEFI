# Как плата работает как машина с UEFI

Отдельной UEFI-прошивки в цепочке нет. Её роль играет U-Boot 2024.04,
собранный с `EFI_LOADER`: он поднимает UEFI-сервисы, находит загрузчик
операционной системы и передаёт ему управление по обычным правилам UEFI.
Для ОС плата при этом неотличима от любой другой машины с UEFI.

## Что включено

| Опция | Что даёт |
|---|---|
| `CONFIG_EFI_LOADER` | сами UEFI-сервисы: протоколы, память, устройства |
| `CONFIG_EFI_BOOTMGR` | загрузочный менеджер и переменные `Boot####`, `BootOrder` |
| `CONFIG_EFI_VARIABLE_FILE_STORE` | EFI-переменные хранятся файлом `ubootefi.var` на ESP |
| `CONFIG_CMD_BOOTEFI` | ручной запуск `.efi`-образа из консоли |
| `CONFIG_CMD_EFIDEBUG` | просмотр и правка загрузочных записей |
| `CONFIG_ENV_IS_IN_MMC`, `CONFIG_ENV_WRITEABLE_LIST` | сохраняемый порядок загрузки, см. [ниже](#сохраняемые-настройки) |
| `CONFIG_CMD_BOOTMENU` | [меню Recovery](#меню-recovery) |

## Что нужно на носителе

Ровно то же, что любой машине с UEFI:

1. Таблица разделов **GPT**.
2. Раздел **ESP** с типом `C12A7328-F81F-11D2-BA4B-00A0C93EC93B` (код `EF00`),
   файловая система FAT32.
3. Внутри него `\EFI\BOOT\BOOTAA64.EFI` — загрузчик ОС.

Ядро и всё остальное лежат где угодно, откуда их прочитает этот загрузчик:
U-Boot умеет FAT и ext4, GRUB — тем более.

## Как выбирается, с чего грузиться

С v3.9 порядок задаётся переменной `tpi_boot_order` — списком меток носителей
через пробел:

| Метка | Носитель |
|---|---|
| `scsi` | SATA SSD |
| `mmc0` | eMMC |
| `mmc2` | microSD |
| `usb` | USB-накопитель |
| `any` | всё, что найдёт U-Boot, включая сеть, — вместе с менеджером `efi_mgr` и записями `Boot####` |

По умолчанию — `scsi mmc0 mmc2 usb any`: SATA, eMMC, microSD, USB, затем всё
остальное. Команда загрузки `run tpi_boot` идёт по списку слева направо, на
каждом носителе ищет загрузочную ОС (`bootflow scan -lbG <метка>`) и запускает
первую найденную. Носители, которых нет в списке, не пробуются. Если не
загрузилось ничего, U-Boot остаётся в консоли и подсказывает, как открыть
[меню Recovery](#меню-recovery).

SATA и USB перед поиском опрашиваются (`scsi scan`, `usb start`): поиск по
метке сам носители не обнаруживает, и без опроса их для `bootflow` ещё нет.

Ключ `-G` выключает для отдельных носителей менеджер `efi_mgr`: без него выбор
зависел бы от EFI-переменных, оставшихся с прошлых загрузок (см. ниже). Отсюда
условие: ОС на SATA, eMMC, microSD и USB должна лежать по стандартному пути
`\EFI\BOOT\BOOTAA64.EFI` на разделе ESP либо иметь `extlinux/extlinux.conf`.
Записи `Boot####` учитываются только на шаге `any`.

На каждом носителе методы пробуются в таком порядке:

- **`extlinux`** — `extlinux/extlinux.conf` или `boot/extlinux/extlinux.conf`
  на любом разделе;
- **`script`** — `boot.scr`;
- **`efi`** — `\EFI\BOOT\BOOTAA64.EFI`. Этот метод **проверяет тип раздела** и
  берёт только разделы с типом ESP. Раздел с посторонним типом в списке
  `bootflow scan -l` не появится вовсе.

Поэтому на одном носителе не стоит держать сразу `extlinux.conf` и ESP:
выиграет `extlinux`.

**Менеджер `efi_mgr`** (шаг `any`) работает иначе: он опирается на
сохранённые EFI-переменные `Boot####` и `BootOrder`, а при их отсутствии
перебирает носители сам. Тип раздела он при этом **не проверяет** — найдёт ESP
и с посторонним типом. Его выбор при нескольких носителях с ESP **не
гарантирован**: он зависит от переменных, оставшихся с прошлых загрузок. До
v3.8 менеджер шёл первым, и порядок SATA/eMMC был непредсказуемым; теперь до
него доходит дело, только если не загрузился ни один носитель из списка.
Кроме того, `any` перебирает носители по своему списку `boot_targets`, в
котором microSD нет.

Посмотреть, что видит загрузчик:

```text
=> bootflow scan -l          # перебрать заново и показать найденное
=> bootflow list             # показать найденное ранее
=> bootflow select 1         # выбрать конкретный
=> bootflow boot             # загрузиться с выбранного
```

Загрузочные записи UEFI:

```text
=> efidebug boot dump
```

## Сохраняемые настройки

Порядок загрузки хранится на eMMC вне разделов, в промежутке 12–16 МиБ между
прошивкой и первым разделом: копия на 12 МиБ (сектор 24576) и резервная на
12 МиБ + 64 КиБ, по 64 КиБ каждая. В заводской раскладке Rockchip
(`parameter.txt`) на этом месте раздел `misc`; ни Debian, ни Astra его не
используют, но форматировать или записывать в него не нужно — это сбросит
порядок загрузки к умолчанию. Формат — обычное окружение U-Boot с CRC32 и
счётчиком: U-Boot читает обе копии и берёт более свежую из целых, а пишет в
другую — оборванная запись не теряет настройки.

Из сохранённого U-Boot берёт **только** `tpi_boot_order`
(`CONFIG_ENV_WRITEABLE_LIST`, список — в
`include/configs/tpi_lazarus_rk3568.h`). Все остальные переменные, включая
скрипты загрузки и меню, всегда приходят из прошивки. Поэтому новая прошивка не
перекрывается старой сохранённой копией, а случайный `saveenv` после
экспериментов в консоли не отключит автозагрузку и не сменит скорость консоли.

Из консоли U-Boot:

```text
=> setenv tpi_boot_order mmc0 scsi mmc2 usb any
=> saveenv
=> env default tpi_boot_order; saveenv      # вернуть порядок по умолчанию
```

Из Linux — сервисной утилитой `tpi-uvon`. Если действительной копии на eMMC
нет — например, после полной очистки носителя, — действует порядок по
умолчанию. Утилита при установке ОС на eMMC промежуток 12–16 МиБ не
перезаписывает, если в образе он пустой, — порядок загрузки переживает
переустановку системы.

## Меню Recovery

Кнопка RECOVERY, удержанная при подаче питания, открывает меню:

```text
  *** U-Boot Boot Menu ***

      RKDevTool: LOADER mode (rockusb, eMMC)
      Boot service medium: microSD
      Boot service medium: USB drive
      USB mass storage: eMMC + SATA SSD
      Continue normal boot
      Boot order: SATA SSD first (default)
      Boot order: eMMC first
      MaskROM mode (BootROM USB download)
      Exit
```

| Пункт | Что делает |
|---|---|
| RKDevTool: LOADER mode | `rockusb 0 mmc 0`: плата видна в RKDevTool и `rkdeveloptool` как LOADER, eMMC открыта для записи. **Пункт по умолчанию**: без выбора он включается через 5 секунд — так, как описано в руководстве на плату. Ctrl+C в консоли — назад в меню |
| Boot service medium | загрузка с microSD или USB-накопителя в обход порядка загрузки — так запускается сервисный носитель |
| USB mass storage | eMMC и SATA SSD видны компьютеру как USB-диски через порт USB-C OTG; выход — Ctrl+C в консоли (назад в меню) или «извлечь» на компьютере. После выхода порядок загрузки перечитывается с eMMC: компьютер мог его изменить |
| Continue normal boot | обычная загрузка по `tpi_boot_order` |
| Boot order | сохранить порядок «сначала SATA» (по умолчанию) или «сначала eMMC» и вернуться в меню |
| MaskROM mode | перезапуск в режим загрузки BootROM — для записи с нуля, когда LOADER не подходит |
| Exit | консоль U-Boot |

Управление — стрелки и Enter, Esc — консоль. Пункты, после которых может
понадобиться что-то ещё (USB-диск, загрузка с отсутствующего носителя, смена
порядка), возвращают в меню. После выхода из меню плата сама не загружается и
остаётся в консоли. Из консоли то же меню открывает `run tpi_recovery`.

В режиме USB-диска плата представляется как `0525:a4a5` — стандартный
mass-storage гаджет Linux, — а не как Rockchip `2207:350a`. На компьютере с
установленным драйвером Rockchip устройство с ID `2207:350a` забирает этот
драйвер, и диск бы не появился. eMMC — первый диск (LUN 0), SATA SSD —
второй (LUN 1), если он подключён. Имя устройства это сообщает: `TPI LAZARUS
UVON: eMMC, SATA` (в LOADER — `TPI LAZARUS UVON: LOADER`), серийный номер —
`serial#` платы, вычисленный из CPU ID, тот же, что видит Linux.

В LOADER плата — Rockchip `2207:350a` с `bcdUSB` 0x0201: по младшему биту
этого поля RKDevTool и `rkdeveloptool` отличают LOADER от MaskROM. Работают
чтение, запись и стирание секторов eMMC, сведения о носителе
(`rkdeveloptool rfi`) и сброс с кодами (ниже).

### Без консоли: LOADER → USB-диск

Пункт меню выбирается в консоли, но консоль не обязательна. Если удержать
RECOVERY при включении и ничего не выбирать, через 5 секунд плата уходит в
LOADER. Сервисная утилита на компьютере видит её там и переводит в режим
USB-диска командой сброса протокола Rockchip с кодом 1 — тем же, что
`rkdeveloptool rd 1` («перезагрузка в mass storage»). Настоящей перезагрузки
нет: rockusb завершается, и меню запускает USB-диск. Когда компьютер
«извлекает» диск, плата перечитывает порядок загрузки с eMMC и грузится как
обычно — в только что записанную систему.

Код 3 (`rkdeveloptool rd 3`) перезапускает плату в MaskROM, остальные коды —
обычный сброс, как раньше.

Кнопка заводит цепь `RECOVERY_KEY` на вход `ADC_VIN0` (SARADC, канал 0): в
отпущенном состоянии там 1,8 В, нажатие замыкает на землю. Плата считает
кнопку нажатой, если три замера подряд с интервалом 10 мс ниже 0,18 В. Общая
проверка Rockchip, которая читает канал 1 и сразу уводит плату в MaskROM,
отключена.

Перезапуск в MaskROM — тёплый сброс. На текущих платах после тёплого сброса
BootROM иногда не видит eMMC (на eMMC выключен вывод аппаратного сброса), и
тогда помогает только снятие питания. Режим LOADER сброса не требует.

## Консоль

С v3.9 консоль U-Boot — **1 500 000 бод, 8N1**, как указано в руководстве на
плату; до v3.8 было 115200. Первые строки после включения — инициализация
DDR, SPL, TF-A и OP-TEE — печатают заводские компоненты, и они остаются на
115200: при 1 500 000 в начале будет несколько строк мусора. Это ожидаемо,
заводские компоненты не меняются.

Скорость консоли Linux задаёт его командная строка (`console=ttyS2,1500000n8`),
поэтому ОС на плате переводится на 1 500 000 вместе с прошивкой.

## Запуск вручную

Если автоматический выбор не устраивает, загрузчик ОС запускается напрямую:

```text
=> fatload mmc 2:1 0x10000000 EFI/BOOT/BOOTAA64.EFI
=> bootefi 0x10000000
```

Так запускается, например, `.efi`-файл, лежащий не по стандартному пути.

## Device tree для операционной системы

U-Boot кладёт свой control DTB в EFI configuration table, и загрузчик ОС может
им воспользоваться. Но обычно ОС подсовывает собственный: GRUB делает это
командой `devicetree`, после чего в журнале ядра видно

```text
EFI stub: Using DTB from configuration table
```

Так устроено потому, что device tree, нужный ядру, богаче того, что достаточно
самому загрузчику.

## Чего здесь нет

- **Secure Boot** не включён: подписи образов не проверяются. Целостность на
  уровне прошивки обеспечивает другое — заводской MiniLoader сверяет SHA-256
  каждого компонента FIT до передачи управления и не запустит повреждённый.
- **Графической оболочки настроек** нет. Порядок загрузки меняется из меню
  Recovery, из консоли U-Boot и утилитой `tpi-uvon` из Linux; остальное — из
  консоли командами `bootflow` и `efidebug`.
- **ACPI** не используется: описание оборудования передаётся через device tree.
